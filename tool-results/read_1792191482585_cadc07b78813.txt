     3→Chapter 10 — Testing
     4→Where we are. Chapter 9 attacked defects before the program runs, with static checking, types, and review.
     5→This chapter attacks them by running the program on chosen inputs and comparing what it does against what
     6→it should do. Testing cannot prove a program correct, but it is the single most practical net for catching the
     7→defects that reviews miss — and the ones a future change will introduce. The central skill is deciding which
     8→tests to write and knowing when you have written enough.
     9→You have already met testing in miniature: run the code, look at the output, decide if it is right. The trouble is that
    10→a real program has more possible inputs than there are atoms in the universe, so “run it and look” does not scale
    11→and does not tell you when to stop. This chapter turns testing from an art into an engineering activity with
    12→criteria: systematic ways to select inputs, to measure how thoroughly you have exercised the code and its
    13→specification, and to justify — to yourself, your team, and sometimes a regulator — the claim that the software
    14→has been tested well enough to ship.
    15→10.1 Overview of Testing
    16→At its simplest, a test records three things: an input or setup, an expected property or result, and the actual
    17→behavior observed when you run it. The test passes when the observed behavior matches what was expected and
    18→fails otherwise. A test suite is a collection of tests run together. This sounds trivial, and for one test it is; the
    19→engineering lives in the four questions the rest of this section raises.
    20→Principle. Testing can reveal the presence of defects but never their absence.1 A passing suite means “no
    21→defect was triggered by these inputs,” not “no defect exists.” Everything in this chapter is about making that
    22→first statement as strong as it can practically be.
    23→10.1.1 Issues during Testing
    24→Four hard problems recur every time you test anything. Name them now, because the rest of the chapter is a set of
    25→answers to them.
    26→Selection. The input space is astronomically large. Which handful of inputs should you actually run?
    27→(§10.1.2, and all of §§10.3–10.6.) And once a suite exists: which of its tests does this change need to run?
    28→(§10.1.6.)
    29→Adequacy. Having run some tests, how do you know whether you have run enough? What is the stopping
    30→rule? (§10.1.3.)

    33→Oracle. For each input, how do you decide whether the observed output is correct? Sometimes that is
    34→harder than producing the output. (§10.1.4.)
    35→Automation and repeatability. A test you cannot re-run cheaply is nearly worthless, because its main
    36→long-term value is catching regressions — old defects reintroduced by new changes. Manual “click around
    37→and see” testing fails this test.
    38→Keep these four in view. A criticism like “your tests are weak” almost always resolves into one of them: you
    39→picked the wrong inputs, you stopped too early, your oracle was too lax, or your tests do not run automatically.
    40→10.1.2 Test Selection
    41→Because you cannot try every input, you must sample the input space — and a random or lazy sample usually
    42→misses the inputs most likely to break. Good selection is criterion-driven: you choose a rule that partitions the
    43→space of possibilities and then pick inputs to satisfy the rule. Two great families of criteria run through this
    44→chapter, and they look at the program from opposite sides:
    45→Black-box (specification-based) selection reads the spec and ignores the code. You pick inputs that
    46→represent distinct required behaviors — valid and invalid classes, boundaries, combinations (§10.4, §10.6).
    47→Its virtue: it finds missing code and survives a rewrite.
    48→White-box (structure-based) selection reads the code and picks inputs that exercise its statements,
    49→branches, and paths (§10.3, §10.5). Its virtue: it finds code the spec-based tests never reached, and it
    50→measures thoroughness precisely.
    51→Neither subsumes the other. A black-box suite can achieve 100% of every code-coverage metric and still miss a
    52→feature that was never implemented (there is no code to cover). A white-box suite can cover every branch of the
    53→code that exists and never notice the branch that should exist. Mature teams use both and measure with both.
    54→10.1.3 Test Adequacy: Deciding When to Stop
    55→“We tested it” is not a stopping rule; “we covered every branch, every equivalence class, and every boundary, and
    56→all tests pass” is. A test-adequacy criterion (also called a coverage criterion) is a checkable condition that tells
    57→you whether a suite is done with respect to that criterion. It converts the vague question “have we tested enough?”
    58→into a countable one.
    59→Most criteria have the shape: there is a set of things to cover, and the suite is adequate when it covers all of them.
    60→The “things” might be statements, branches, paths, equivalence classes, boundaries, or condition-outcome pairs.
    61→Coverage is then the fraction covered:
    62→coverage =
    63→items exercised by the suite
    64→total items required by the criterion

    67→Coverage is a floor, not a ceiling: 100% branch coverage means every branch ran, not that every branch is correct.
    68→But low coverage is a genuine alarm — code that never ran under any test is code you know nothing about
    69→empirically.
    70→Pitfall. Do not manage to a coverage number for its own sake. A team told “hit 90%” can write assertion-
    71→free tests that execute code without checking it, gaming the metric while learning nothing. Coverage is a
    72→diagnostic, not a goal; pair it always with meaningful oracles (§10.1.4).
    73→10.1.4 Test Oracles: Evaluating the Response to a Test
    74→An oracle is whatever decides, for a given input, whether the actual output is correct. In a textbook example the
    75→oracle is obvious — you write assert add(2, 3) == 5, and 5 is the oracle. In real systems it is often the hardest
    76→part of testing, a difficulty known as the oracle problem.2 If you are testing a function that renders a map, or
    77→ranks search results, or predicts weather, what exactly should you compare against?
    78→Several oracle strategies, from strongest to weakest:
    79→Exact expected value. You know the right answer and hard-code it: assert reverse("abc") == "cba".
    80→Strongest, but only available when you can compute the answer independently.
    81→Property / invariant oracle. You cannot name the exact answer but you know a property it must satisfy.
    82→For a sort: the output is a permutation of the input and is non-decreasing. For encryption:
    83→decrypt(encrypt(x)) == x (a round-trip oracle). These power property-based testing, where a tool
    84→generates many random inputs and checks the property on each.
    85→Cross-check / differential oracle. Compare against an independent implementation — a slow reference
    86→version, a previous release, or a competitor. If they disagree, at least one is wrong.
    87→Human judgment. A person inspects the output. Necessary for look-and-feel, but slow, non-repeatable,
    88→and the enemy of automation — use it sparingly.
    89→Consider a function median(xs). An exact oracle requires you to know the median of each test list. A cheaper
    90→property oracle: after sorting, the result equals the middle element; and median(xs) == median(reversed(xs))
    91→(order independence). Property oracles let you throw thousands of generated inputs at the function without hand-
    92→computing each answer — often the difference between a suite that finds real defects and one that only confirms
    93→the three cases you already thought of.

    98→10.1.5 Mutation Testing: Grading Your Suite
    99→Coverage tells you what your tests ran; it cannot tell you what they would catch. The pitfall in §10.1.3 —
   100→assertion-free tests that execute everything and check nothing — scores 100% on any coverage criterion while
   101→detecting no defects at all. Mutation testing closes that gap by testing the tests.3
   102→Principle — never trust a test you have never seen fail. A passing test is evidence only if you know the
   103→test can detect the defect it claims to guard against. Before you trust a new test, temporarily remove or break
   104→the behavior under test and confirm the test turns red for the reason you expected; then restore the behavior
   105→and watch it return to green.4 Seeing a test fail once does not prove it catches every defect, but never seeing
   106→it fail leaves a more basic question unanswered — does the test test anything? An assertion may never
   107→execute, the runner may discover no tests, a mock may intercept the wrong boundary, or the expected value
   108→may reproduce the very mistake the implementation makes. Test-driven development (§2.3.2) runs this
   109→check at birth — red first, then green; mutation testing applies the same idea to an established suite by
   110→inserting defects and asking whether the tests notice.
   111→A mutation tool takes your working code and plants small, deliberate defects called mutants: flip a < to <=,
   112→change a constant by one, negate a condition, delete a statement. Each mutant is a plausible bug — exactly the
   113→kind a tired programmer writes. The tool then reruns your suite against each mutant in turn:
   114→If at least one test fails, the suite noticed the defect: the mutant is killed.
   115→If every test still passes, the mutant is a survivor — your suite executed the broken line and did not notice.
   116→The mutation score — mutants killed divided by mutants generated — grades your suite’s defect-detecting
   117→strength in a way coverage never can. Better, nearly every survivor is actionable: it points at a specific line where
   118→an assertion is weak or missing.

   141→10.1.6 Selecting from the Suite: Regression Selection and Prioritization
   142→Everything so far selects inputs — it builds the suite. A second selection problem appears once the suite exists and
   143→keeps growing: on every change, which of the tests you already have should run, and in what order? Early in a
   144→project the answer is “all of them, every time,” and you should keep that answer for as long as you can. But suites
   145→grow with their codebase, and eventually the full run no longer fits the feedback loop it exists to power — one
   146→industrial team reported a suite that took seven weeks to run in full.5 The moment there is a budget, three
   147→techniques share the work, and the vocabulary is worth knowing:
   148→Minimization permanently deletes tests that no longer earn their runtime: redundant (everything they
   149→exercise, another test also exercises) or obsolete (the behavior they check no longer exists).
   150→Selection picks, per change, the subset of tests relevant to what changed. A CSS change does not need the
   151→payroll calculation suite — if you can establish which tests a change can possibly affect.
   152→Prioritization keeps every test but orders the run so likely failures come first. Feedback arrives when the
   153→first test fails, not when the last one passes; researchers score an ordering by its rate of fault detection
   154→(APFD).5
   155→The subtle point is that a time budget changes what “best” means. Suppose your merge gate has a ten-minute
   156→budget (§14.2.4), and history gives you a value estimate for each test — say, the distinct regressions each one has
   157→caught over the past year:

   182→values overlap: two tests that exercise the same code catch the same defects, so a selection’s value is less than the
   183→sum of its parts. Practical approaches therefore lean on heuristics and search — knapsack approximations and
   184→genetic algorithms have both been studied6 — and large CI systems apply the same idea as predictive test
   185→selection, weighting each test by its failure history and its relevance to the changed files.

   187→explicitly what runs at the merge gate and what runs continuously behind it (§14.2.4), and never let “the
   188→suite is slow” drift into “we don’t run the suite.”

   191→answers a different question and catches a different class of defect, and the levels are complementary, not

   274→10.2.3 Functional, System, and Acceptance Testing
   275→Higher levels test the assembled product against ever-broader notions of “correct”:
   276→Functional testing checks that a complete feature behaves per its specification, treating the system as a
   277→black box: given a shopping cart with these items and this coupon, the checkout total is X. It spans many
   278→units but is scoped to one function of the product.
   279→System testing exercises the entire, integrated system in a production-like environment, including non-
   280→functional requirements — performance, security, reliability, usability. “The page loads in under 500 ms at
   281→1,000 concurrent users” is a system-level test.
   282→Acceptance testing answers the customer’s question, “will I sign for this?” It is run against the customer’s
   283→own criteria, often by or with the customer. User acceptance testing (UAT) uses real users and realistic
   284→tasks; alpha/beta releases are acceptance testing in the wild.

   316→10.2.4 Case Study: Test Early and Often — the Testing Pyramid
   317→The levels are not equally cheap. A good unit test runs in milliseconds and almost never flakes; a full end-to-end
   318→(E2E) test may spin up a browser, a database, and three services, take minutes, and fail intermittently for reasons
   319→that have nothing to do with your code. This cost gradient motivates the testing pyramid: have many fast unit
   320→tests, fewer integration tests, and only a handful of slow end-to-end tests.11
   321→
   322→===== صفحة الكتاب 263 =====
   323→The pyramid is an economic argument. Suppose a defect in the discount logic could be caught at any level. Caught
   324→by a unit test, the feedback arrives in seconds, on the exact line, before you even commit. Caught by an E2E test
   325→in CI, it arrives twenty minutes later as “checkout total was wrong,” and you must debug down to the line. Caught
   326→in production, it arrives as a customer complaint and a refund. The cost of a defect typically rises substantially
   327→with each stage it survives — the exact multiplier varies by domain, tooling, and release process (§2.4.2) — so
   328→you push detection as far down and early as it will go.12
   329→Pitfall — the ice-cream cone. Teams that skip unit tests and lean on a big pile of slow, flaky E2E tests
   330→invert the pyramid into an “ice-cream cone.” Their CI is slow, failures are hard to localize, and developers
   331→learn to ignore red builds (“probably just flaky”). An ignored test suite protects nothing. Prefer the pyramid
   332→deliberately.
   333→Because flakiness is what poisons trust, know its causes. A flaky test — one that passes and fails across runs with
   334→no code change — most often traces to one of four roots: race conditions and async timing (the assertion runs
   335→before the work finishes); shared mutable state between tests (one test’s leftovers change another’s result); test-
   336→order dependence (the suite passes in one order and fails in another); or unstable external dependencies (real
   337→networks, real clocks, third-party services).13 The fixes mirror the causes: isolate state so each test builds and tears
   338→down its own world; make tests order-independent (and let the runner randomize order to prove it); await
   339→asynchronous work properly with sane timeouts instead of sleeping and hoping; and replace or fake unstable
   340→dependencies. For the incorrigible case, quarantine the test out of the gating suite — then fix it or delete it,
   341→because a test allowed to stay red-then-green trains the team to ignore the suite.
   342→

   348→10.3 Code Coverage I: White-Box Testing
   349→White-box testing selects inputs by looking at the code’s structure. To talk about structure precisely, we model a
   350→function as a graph.
   351→10.3.1 Control-Flow Graphs
   352→A control-flow graph (CFG) represents a function as a directed graph: nodes are basic blocks (maximal straight-
   353→line sequences of statements), and edges are the possible transfers of control between them. A branch (an if, a
   354→loop condition) is a node with two outgoing edges; a merge is a node with two incoming edges. The CFG makes
   355→“statements,” “branches,” and “paths” into things you can count.
   356→Consider a function that classifies a number and, for positive numbers, sums 1..n:
   357→Its control-flow graph:

   359→if n < 0:                   # node 2  (decision)
   360→return "negative"
   361→# node 3
   362→total = 0
   363→# node 4
   364→i = 1
   365→# node 4
   366→while i <= n:               # node 5  (decision)
   367→total += i              # node 6
   368→i += 1
   369→# node 6
   370→return f"sum={total}"
   371→# node 7  (exit)

   439→entirely: modern CPUs already record where they branch, and sampling those hardware monitors during a
   440→test run recovered up to ~90% of branch coverage with less overhead and no code growth — enough to
   441→measure coverage on the device a mobile app actually ships to.6

   514→pipeline stage (Chapter 14), not on the every-commit path.
