    28→6.1 Layers and Modules
    29→When we first introduced neural networks, we focused on linear models with a single out-
    30→put. Here, the entire model consists of just a single neuron. Note that a single neuron (i)
    31→takes some set of inputs; (ii) generates a corresponding scalar output; and (iii) has a set of
    32→associated parameters that can be updated to optimize some objective function of interest.
    33→Then, once we started thinking about networks with multiple outputs, we leveraged vec-
    34→torized arithmetic to characterize an entire layer of neurons. Just like individual neurons,

    40→layers (i) take a set of inputs, (ii) generate corresponding outputs, and (iii) are described by
    41→a set of tunable parameters. When we worked through softmax regression, a single layer
    42→was itself the model. However, even when we subsequently introduced MLPs, we could
    43→still think of the model as retaining this same basic structure.
    44→Interestingly, for MLPs, both the entire model and its constituent layers share this structure.
    45→The entire model takes in raw inputs (the features), generates outputs (the predictions), and
    46→possesses parameters (the combined parameters from all constituent layers). Likewise,
    47→each individual layer ingests inputs (supplied by the previous layer) generates outputs (the
    48→inputs to the subsequent layer), and possesses a set of tunable parameters that are updated
    49→according to the signal that flows backwards from the subsequent layer.
    50→While you might think that neurons, layers, and models give us enough abstractions to go
    51→about our business, it turns out that we often find it convenient to speak about components
    52→that are larger than an individual layer but smaller than the entire model. For example, the
    53→ResNet-152 architecture, which is wildly popular in computer vision, possesses hundreds of
    54→layers. These layers consist of repeating patterns of groups of layers. Implementing such
    55→a network one layer at a time can grow tedious. This concern is not just hypothetical—
    56→such design patterns are common in practice. The ResNet architecture mentioned above
    57→won the 2015 ImageNet and COCO computer vision competitions for both recognition and
    58→detection (He et al., 2016) and remains a go-to architecture for many vision tasks. Similar
    59→architectures in which layers are arranged in various repeating patterns are now ubiquitous
    60→in other domains, including natural language processing and speech.
    61→To implement these complex networks, we introduce the concept of a neural network mod-
    62→ule. A module could describe a single layer, a component consisting of multiple layers,
    63→or the entire model itself! One benefit of working with the module abstraction is that they
    64→can be combined into larger artifacts, often recursively. This is illustrated in Fig. 6.1.1.
    65→By defining code to generate modules of arbitrary complexity on demand, we can write
    66→surprisingly compact code and still implement complex neural networks.

   101→6.1.1 A Custom Module
   102→Perhaps the easiest way to develop intuition about how a module works is to implement
   103→one ourselves. Before we do that, we briefly summarize the basic functionality that each
   104→module must provide:
   105→1. Ingest input data as arguments to its forward propagation method.
   106→2. Generate an output by having the forward propagation method return a value. Note
   107→that the output may have a different shape from the input. For example, the first fully
   108→connected layer in our model above ingests an input of arbitrary dimension but returns
   109→an output of dimension 256.
   110→3. Calculate the gradient of its output with respect to its input, which can be accessed via
   111→its backpropagation method. Typically this happens automatically.
   112→

   114→210
   115→Builders’ Guide
   116→4. Store and provide access to those parameters necessary for executing the forward prop-
   117→agation computation.
   118→5. Initialize model parameters as needed.
   119→In the following snippet, we code up a module from scratch corresponding to an MLP
   120→with one hidden layer with 256 hidden units, and a 10-dimensional output layer. Note that
   121→the MLP class below inherits the class that represents a module. We will heavily rely on
   122→the parent class’s methods, supplying only our own constructor (the __init__ method in
   123→Python) and the forward propagation method.
   124→class MLP(nn.Module):
   125→def __init__(self):
   126→# Call the constructor of the parent class nn.Module to perform
   127→# the necessary initialization
   128→super().__init__()
   129→self.hidden = nn.LazyLinear(256)
   130→self.out = nn.LazyLinear(10)
   131→# Define the forward propagation of the model, that is, how to return the
   132→# required model output based on the input X
   133→def forward(self, X):
   134→return self.out(F.relu(self.hidden(X)))
   135→Let’s first focus on the forward propagation method. Note that it takes X as input, calcu-
   136→lates the hidden representation with the activation function applied, and outputs its logits.
   137→In this MLP implementation, both layers are instance variables. To see why this is reason-
   138→able, imagine instantiating two MLPs, net1 and net2, and training them on different data.
   139→Naturally, we would expect them to represent two different learned models.
   140→We instantiate the MLP’s layers in the constructor and subsequently invoke these layers on
   141→each call to the forward propagation method. Note a few key details. First, our customized
   142→__init__ method invokes the parent class’s __init__ method via super().__init__()
   143→sparing us the pain of restating boilerplate code applicable to most modules. We then
   144→instantiate our two fully connected layers, assigning them to self.hidden and self.out.
   145→Note that unless we implement a new layer, we need not worry about the backpropagation
   146→method or parameter initialization. The system will generate these methods automatically.
   147→Let’s try this out.
   148→net = MLP()

   159→6.1.2 The Sequential Module
   160→We can now take a closer look at how the Sequential class works. Recall that Sequen-
   161→tial was designed to daisy-chain other modules together. To build our own simplified
   162→MySequential, we just need to define two key methods:
   163→1. A method for appending modules one by one to a list.
   164→2. A forward propagation method for passing an input through the chain of modules, in the
   165→same order as they were appended.
   166→The following MySequential class delivers the same functionality of the default Sequen-
   167→tial class.
   168→class MySequential(nn.Module):
   169→def __init__(self, *args):
   170→super().__init__()
   171→for idx, module in enumerate(args):
   172→self.add_module(str(idx), module)
   173→def forward(self, X):
   174→for module in self.children():
   175→X = module(X)
   176→return X
   177→In the __init__ method, we add every module by calling the add_modules method. These
   178→modules can be accessed by the children method at a later date. In this way the system
   179→knows the added modules, and it will properly initialize each module’s parameters.
   180→When our MySequential’s forward propagation method is invoked, each added module is
   181→executed in the order in which they were added. We can now reimplement an MLP using
   182→our MySequential class.
   183→net = MySequential(nn.LazyLinear(256), nn.ReLU(), nn.LazyLinear(10))
   184→net(X).shape
   185→torch.Size([2, 10])
   186→Note that this use of MySequential is identical to the code we previously wrote for the
   187→Sequential class (as described in Section 5.1).
   188→6.1.3 Executing Code in the Forward Propagation Method
   189→The Sequential class makes model construction easy, allowing us to assemble new archi-
   190→tectures without having to define our own class. However, not all architectures are simple
   191→daisy chains. When greater flexibility is required, we will want to define our own blocks.
   192→For example, we might want to execute Python’s control flow within the forward propaga-
   193→tion method. Moreover, we might want to perform arbitrary mathematical operations, not
   194→simply relying on predefined neural network layers.

   199→You may have noticed that until now, all of the operations in our networks have acted upon
   200→our network’s activations and its parameters. Sometimes, however, we might want to in-
   201→corporate terms that are neither the result of previous layers nor updatable parameters. We
   202→call these constant parameters. Say for example that we want a layer that calculates the
   203→function 𝑓(x, w) = 𝑐· w⊤x, where x is the input, w is our parameter, and 𝑐is some speci-
   204→fied constant that is not updated during optimization. So we implement a FixedHiddenMLP
   205→class as follows.
   206→class FixedHiddenMLP(nn.Module):
   207→def __init__(self):
   208→super().__init__()
   209→# Random weight parameters that will not compute gradients and
   210→# therefore keep constant during training
   211→self.rand_weight = torch.rand((20, 20))
   212→self.linear = nn.LazyLinear(20)
   213→def forward(self, X):
   214→X = self.linear(X)
   215→X = F.relu(X @ self.rand_weight + 1)
   216→# Reuse the fully connected layer. This is equivalent to sharing
   217→# parameters with two fully connected layers
   218→X = self.linear(X)
   219→# Control flow
   220→while X.abs().sum() > 1:
   221→X /= 2
   222→return X.sum()

   224→tialized randomly at instantiation and are thereafter constant. This weight is not a model
   225→parameter and thus it is never updated by backpropagation. The network then passes the
   226→output of this “fixed” layer through a fully connected layer.
   227→Note that before returning the output, our model did something unusual. We ran a while-
   228→loop, testing on the condition its ℓ1 norm is larger than 1, and dividing our output vector
   229→by 2 until it satisfied the condition. Finally, we returned the sum of the entries in X. To our
   230→knowledge, no standard neural network performs this operation. Note that this particular
   231→operation may not be useful in any real-world task. Our point is only to show you how to

   493→6.4 Lazy Initialization
   494→So far, it might seem that we got away with being sloppy in setting up our networks. Specif-
   495→ically, we did the following unintuitive things, which might not seem like they should
   496→work:
   497→• We defined the network architectures without specifying the input dimensionality.
   498→• We added layers without specifying the output dimension of the previous layer.
   499→• We even “initialized” these parameters before providing enough information to deter-
   500→mine how many parameters our models should contain.
   501→You might be surprised that our code runs at all. After all, there is no way the deep learning
   502→framework could tell what the input dimensionality of a network would be. The trick here
   503→is that the framework defers initialization, waiting until the first time we pass data through
   504→the model, to infer the sizes of each layer on the fly.
   505→Later on, when working with convolutional neural networks, this technique will become
   506→even more convenient since the input dimensionality (e.g., the resolution of an image) will
   507→affect the dimensionality of each subsequent layer. Hence the ability to set parameters
   508→without the need to know, at the time of writing the code, the value of the dimension can
   509→greatly simplify the task of specifying and subsequently modifying our models. Next, we
   510→go deeper into the mechanics of initialization.
   511→import torch
   512→from torch import nn
   513→from d2l import torch as d2l

   900→Side Notes
   901→People use GPUs to do machine learning because they expect them to be fast. But trans-
   902→ferring variables between devices is slow: much slower than computation. So we want you
   903→to be 100% certain that you want to do something slow before we let you do it. If the deep
   904→learning framework just did the copy automatically without crashing then you might not
   905→realize that you had written some slow code.
   906→Transferring data is not only slow, it also makes parallelization a lot more difficult, since
   907→we have to wait for data to be sent (or rather to be received) before we can proceed with
   908→more operations. This is why copy operations should be taken with great care. As a rule of
   909→thumb, many small operations are much worse than one big operation. Moreover, several
   910→operations at a time are much better than many single operations interspersed in the code
   911→unless you know what you are doing. This is the case since such operations can block if
   912→one device has to wait for the other before it can do something else. It is a bit like ordering
   913→your coffee in a queue rather than pre-ordering it by phone and finding out that it is ready
   914→when you are.
   915→Last, when we print tensors or convert tensors to the NumPy format, if the data is not in the
   916→main memory, the framework will copy it to the main memory first, resulting in additional
   917→transmission overhead. Even worse, it is now subject to the dreaded global interpreter lock
   918→that makes everything wait for Python to complete.

   963→learning framework requires all input data for calculation to be on the same device, be it
   964→CPU or the same GPU. You can lose significant performance by moving data without care.
   965→A typical mistake is as follows: computing the loss for every minibatch on the GPU and
   966→reporting it back to the user on the command line (or logging it in a NumPy ndarray) will
   967→trigger a global interpreter lock which stalls all GPUs. It is much better to allocate memory
   968→for logging inside the GPU and only move larger logs.
