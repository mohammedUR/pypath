   543→13.4.2 Memory
   544→At its most basic memory is used to store data that needs to be readily accessible. At
   545→present CPU RAM is typically of the DDR4 191 variety, offering 20–25 GB/s bandwidth
   546→per module. Each module has a 64-bit-wide bus. Typically pairs of memory modules are
   547→used to allow for multiple channels. CPUs have between 2 and 4 memory channels, i.e.,
   548→they have between 4 0GB/s and 100 GB/s peak memory bandwidth. Often there are two
   549→banks per channel. For instance AMD’s Zen 3 Threadripper has 8 slots.
   550→While these numbers are impressive, indeed, they only tell part of the story. When we
   551→want to read a portion from memory we first need to tell the memory module where the
   552→information can be found. That is, we first need to send the address to RAM. Once this
   553→is accomplished we can choose to read just a single 64 bit record or a long sequence of
   554→records. The latter is called burst read. In a nutshell, sending an address to memory and
   555→setting up the transfer takes approximately 100 ns (details depend on the specific timing
   556→coefficients of the memory chips used), every subsequent transfer takes only 0.2 ns. In
   557→short, the first read is 500 times as expensive as subsequent ones! Note that we could
   558→perform up to 10,000,000 random reads per second. This suggests that we avoid random
   559→memory access as far as possible and use burst reads (and writes) instead.
   560→Matters are a bit more complex when we take into account that we have multiple banks.
   561→Each bank can read memory largely independently. This means two things. On the one
   562→hand, the effective number of random reads is up to 4 times higher, provided that they are
   563→spread evenly across memory. It also means that it is still a bad idea to perform random
   564→reads since burst reads are 4 times faster, too. On the other hand, due to memory alignment
   565→to 64 bit boundaries it is a good idea to align any data structures with the same boundaries.
   566→Compilers do this pretty much automatically192 when the appropriate flags are set. Curious
   567→readers are encouraged to review a lecture on DRAMs such as the one by Zeshan Chishti
   568→193.
   569→GPU memory is subject to even higher bandwidth requirements since they have many more
   570→processing elements than CPUs. By and large there are two options to address them. The
   571→first is to make the memory bus significantly wider. For instance, NVIDIA’s RTX 2080
   572→Ti has a 352-bit-wide bus. This allows for much more information to be transferred at
   573→the same time. Second, GPUs use specific high-performance memory. Consumer-grade
   574→devices, such as NVIDIA’s RTX and Titan series typically use GDDR6194 chips with over
   575→500 GB/s aggregate bandwidth. An alternative is to use HBM (high bandwidth memory)
   576→modules. They use a very different interface and connect directly with GPUs on a dedicated

   587→13.4.3 Storage
   588→We saw that some of the key characteristics of RAM are bandwidth and latency. The same
   589→is true for storage devices, just that the differences can be even more extreme.
   590→Hard Disk Drives
   591→Hard disk drives (HDDs) have been in use for over half a century. In a nutshell they contain
   592→a number of spinning platters with heads that can be positioned to read or write at any given
   593→track. High-end disks hold up to 16 TB on 9 platters. One of the key benefits of HDDs
   594→is that they are relatively inexpensive. One of their many downsides are their typically
   595→catastrophic failure modes and their relatively high read latency.
   596→To understand the latter, consider the fact that HDDs spin at around 7,200 RPM (revolutions
   597→per minute). If they were much faster they would shatter due to the centrifugal force exerted
   598→on the platters. This has a major downside when it comes to accessing a specific sector
   599→on the disk: we need to wait until the platter has rotated in position (we can move the
   600→heads but not accelerate the actual disks). Hence it can take over 8 ms until the requested
   601→data is available. A common way this is expressed is to say that HDDs can operate at
   602→approximately 100 IOPs (input/output operations per second). This number has essentially
   603→remained unchanged for the past two decades. Worse still, it is equally difficult to increase
   604→bandwidth (it is in the order of 100–200 MB/s). After all, each head reads a track of bits,
   605→hence the bit rate only scales with the square root of the information density. As a result,
   606→HDDs are quickly becoming relegated to archival storage and low-grade storage for very
   607→large datasets.
   608→Solid State Drives
   609→Solid state drives (SSDs) use flash memory to store information persistently. This allows
   610→for much faster access to stored records. Modern SSDs can operate at 100,000 to 500,000
   611→IOPs, i.e., up to 3 orders of magnitude faster than HDDs. Furthermore, their bandwidth
   612→can reach 1–3GB/s, i.e., one order of magnitude faster than HDDs. These improvements
   613→sound almost too good to be true. Indeed, they come with the following caveats, due to the
   614→way SSDs are designed.
   615→• SSDs store information in blocks (256 KB or larger). They can only be written as a whole,
   616→which takes significant time. Consequently bit-wise random writes on SSD have very
   617→poor performance. Likewise, writing data in general takes significant time since the
   618→block has to be read, erased and then rewritten with new information. By now SSD
   619→

   623→controllers and firmware have developed algorithms to mitigate this. Nonetheless,
   624→writes can be much slower, in particular for QLC (quad level cell) SSDs. The key

   626→write in large blocks if possible.
   627→• The memory cells in SSDs wear out relatively quickly (often already after a few thousand
   628→writes). Wear-level protection algorithms are able to spread the degradation over many
   629→cells. That said, it is not recommended to use SSDs for swapping files or for large
   630→aggregations of log-files.
   631→• Lastly, the massive increase in bandwidth has forced computer designers to attach SSDs

   638→as chosen by users. We recommend that users increase the provisioned number of IOPs

   661→Each of the processor cores consists of a rather sophisticated set of components. While

   702→Cache
   703→Consider the following situation: we have a modest CPU core with 4 cores as depicted in
   704→Fig. 13.4.3 above, running at 2 GHz frequency. Moreover, let’s assume that we have an IPC
   705→(instructions per clock) count of 1 and that the units have AVX2 with 256-bit width enabled.
   706→Let’s furthermore assume that at least one of the registers used for AVX2 operations needs
   707→to be retrieved from memory. This means that the CPU consumes 4 × 256 bit = 128 bytes
   708→of data per clock cycle. Unless we are able to transfer 2 × 109 × 128 = 256 × 109 bytes
   709→to the processor per second the processing elements are going to starve. Unfortunately the
   710→memory interface of such a chip only supports 20–40 GB/s data transfer, i.e., one order of
   711→magnitude less. The fix is to avoid loading new data from memory as far as possible and
   712→rather to cache it locally on the CPU. This is where caches come in handy. Commonly the
   713→following names or concepts are used:
   714→• Registers are strictly speaking not part of the cache. They help stage instructions. That
   715→said, CPU registers are memory locations that a CPU can access at clock speed with-
   716→out any delay penalty. CPUs have tens of registers. It is up to the compiler (or pro-
   717→grammer) to use registers efficiently. For instance the C programming language has a
   718→register keyword.
   719→• L1 caches are the first line of defense against high memory bandwidth requirements.
   720→L1 caches are tiny (typical sizes might be 32–64 KB) and often split into data and
   721→instructions caches. When data is found in the L1 cache, access is very fast. If they
   722→cannot be found there, the search progresses down the cache hierarchy.
   723→• L2 caches are the next stop. Depending on architecture design and processor size they
   724→might be exclusive. They might be accessible only by a given core or shared among
   725→multiple cores. L2 caches are larger (typically 256–512 KB per core) and slower than
   726→

   730→L1. Furthermore, to access something in L2 we first need to check to realize that the
   731→data is not in L1, which adds a small amount of extra latency.
   732→• L3 caches are shared among multiple cores and can be quite large. AMD’s Epyc 3 server
   733→CPUs have a whopping 256 MB of cache spread across multiple chiplets. More typical
   734→numbers are in the 4–8 MB range.
   735→Predicting which memory elements will be needed next is one of the key optimization pa-
   736→rameters in chip design. For instance, it is advisable to traverse memory in a forward direc-
   737→tion since most caching algorithms will try to read ahead rather than backwards. Likewise,
   738→keeping memory access patterns local is a good way of improving performance.
   739→Adding caches is a double-edge sword. On the one hand they ensure that the processor
   740→cores do not starve of data. At the same time they increase chip size, using up area that
   741→otherwise could have been spent on increasing processing power. Moreover, cache misses
   742→can be expensive. Consider the worst case scenario, false sharing, as depicted in Fig. 13.4.6.
   743→A memory location is cached on processor 0 when a thread on processor 1 requests the
   744→data. To obtain it, processor 0 needs to stop what it is doing, write the information back
   745→to main memory and then let processor 1 read it from memory. During this operation both
   746→processors wait. Quite potentially such code runs more slowly on multiple processors when
   747→compared with an efficient single-processor implementation. This is one more reason for
   748→why there is a practical limit to cache sizes (besides their physical size).

   831→13.4.6 Networks and Buses
   832→Whenever a single device is insufficient for optimization we need to transfer data to and
   833→from it to synchronize processing. This is where networks and buses come in handy. We
   834→have a number of design parameters: bandwidth, cost, distance, and flexibility. On one end
   835→we have WiFi that has a pretty good range, is very easy to use (no wires, after all), cheap but
   836→it offers comparatively mediocre bandwidth and latency. No machine learning researcher
   837→within their right mind would use it to build a cluster of servers. In what follows we focus
   838→on interconnects that are suitable for deep learning.
   839→• PCIe is a dedicated bus for very high bandwidth point-to-point connections (up to 32
   840→GB/s on PCIe 4.0 in a 16-lane slot) per lane. Latency is in the order of single-digit
   841→microseconds (5 μs). PCIe links are precious. Processors only have a limited number
   842→of them: AMD’s EPYC 3 has 128 lanes, Intel’s Xeon has up to 48 lanes per chip;
   843→on desktop-grade CPUs the numbers are 20 (Ryzen 9) and 16 (Core i9) respectively.
   844→Since GPUs have typically 16 lanes, this limits the number of GPUs that can connect
   845→to the CPU at full bandwidth. After all, they need to share the links with other high
   846→bandwidth peripherals such as storage and Ethernet. Just like with RAM access, large
   847→bulk transfers are preferable due to reduced packet overhead.
   848→• Ethernet is the most commonly used way of connecting computers. While it is signifi-
   849→cantly slower than PCIe, it is very cheap and resilient to install and covers much longer
   850→distances. Typical bandwidth for low-grade servers is 1 GBit/s. Higher-end devices
   851→(e.g., C5 instances 200 in the cloud) offer between 10 and 100 GBit/s bandwidth. As
   852→in all previous cases data transmission has significant overheads. Note that we al-
   853→most never use raw Ethernet directly but rather a protocol that is executed on top of
   854→the physical interconnect (such as UDP or TCP/IP). This adds further overhead. Like
   855→PCIe, Ethernet is designed to connect two devices, e.g., a computer and a switch.
   856→• Switches allow us to connect multiple devices in a manner where any pair of them can
   857→carry out a (typically full bandwidth) point-to-point connection simultaneously. For
   858→instance, Ethernet switches might connect 40 servers at high cross-sectional band-
   859→width. Note that switches are not unique to traditional computer networks. Even PCIe
   860→lanes can be switched201 . This occurs, e.g., to connect a large number of GPUs to a
   861→host processor, as is the case for the P2 instances202.
   862→• NVLink is an alternative to PCIe when it comes to very high bandwidth interconnects.
   863→It offers up to 300 Gbit/s data transfer rate per link. Server GPUs (Volta V100) have
   864→six links whereas consumer-grade GPUs (RTX 2080 Ti) have only one link, operating
   865→at a reduced 100 Gbit/s rate. We recommend to use NCCL 203 to achieve high data
   866→transfer between GPUs.

   995→13.4.8 Summary
   996→• Devices have overheads for operations. Hence it is important to aim for a small number
   997→of large transfers rather than many small ones. This applies to RAM, SSDs, networks
   998→and GPUs.
   999→• Vectorization is key for performance. Make sure you are aware of the specific abilities
  1000→of your accelerator. E.g., some Intel Xeon CPUs are particularly good for INT8 op-
  1001→erations, NVIDIA Volta GPUs excel at FP16 matrix-matrix operations and NVIDIA
  1002→Turing shines at FP16, INT8, and INT4 operations.
  1003→• Numerical overflow due to small data types can be a problem during training (and to a
  1004→lesser extent during inference).
  1005→• Aliasing can significantly degrade performance. For instance, memory alignment on 64
  1006→bit CPUs should be done with respect to 64 bit boundaries. On GPUs it is a good idea
  1007→to keep convolution sizes aligned, e.g., to tensor cores.
  1008→• Match your algorithms to the hardware (e.g., memory footprint, and bandwidth). Great
  1009→speedup (orders of magnitude) can be achieved when fitting the parameters into caches.
  1010→• We recommend that you sketch out the performance of a novel algorithm on paper before
  1011→verifying the experimental results. Discrepancies of an order-of-magnitude or more
  1012→are reasons for concern.
  1013→• Use profilers to debug performance bottlenecks.
  1014→• Training and inference hardware have different sweet spots in terms of price and perfor-
  1015→mance.
